# Архитектура

`main.py` управляет lifespan движка и HTTP-клиента, CORS, логированием,
ошибками, health и подключением маршрутов. `bootstrap.py` связывает порты.
Domain — dataclasses и чистые функции; application — сценарии и порты;
infrastructure — ORM, PostgreSQL UoW, Argon2, настройки, HTTP AI и parser;
presentation — Pydantic, APIRouter, зависимости и преобразование HTTP.
Архитектурный тест проверяет направление импортов.

Store — небольшой типизированный порт работы с доменными записями внутри
UoW. Это не общий наследуемый сервис. Модули не получают ORM или AsyncSession;
сквозные сценарии координируют доменные контракты через общий UoW.
ORM-строки отделены от доменных dataclasses. Основные связи — FK и уникальные
ограничения; JSONB хранит снимки и объяснения. SkillClaim/ExperienceClaim
нормализованы как разновидности VerificationRequest, Preference — поля User.

Команды выполняются в одной транзакции: идемпотентность, бизнес-изменения,
история и аудит. Advisory lock ограничен пользователем/операцией/ключом.
Изменения навыков сначала блокируют Employee; эффекты обходятся в порядке
skill_id. Уникальные VerificationReview.request_id и
ActivityCompletion.enrollment_id запрещают повторное применение с новым
ключом. Откат не оставляет частичных эффектов. Репозитории не делают commit.

Каталог, импорт и создание снимков сериализуются advisory lock `catalog`.
Рекомендации: согласованный снимок → закрытие транзакции → AI с бюджетом →
новая транзакция, блокировка профиля и повторная проверка версий → сохранение.
profile/history/catalog/policy/requirements versions плюс business_date и
locale определяют актуальность. UI-mode не меняет профильную версию.

Подтверждённые навыки — единственный источник matching. Coverage — среднее
отношение verified/required с ограничением 1, без нулевых требований.
Отсутствие требований даёт null. Готовность определяется всеми требованиями,
а не округлением coverage. Официальная роль меняется только PromotionReview.
What-if и реальные начисления используют одну функцию apply_effect.

Локальная авторизация: Argon2, случайный непрозрачный bearer, SHA-256 токена
в БД, срок по реальному UTC и отзыв. Ограничения попыток входа и затратных
запросов находятся в памяти одного процесса; перезапуск сбрасывает окна.
Для нескольких воркеров нужен внешний общий limiter. В Compose один воркер.
Логи содержат request_id, шаблон маршрута, длительность и HTTP-статус.
Пароли, токены, evidence и полный профиль не журналируются.

Readiness проверяет доступность БД и revision Alembic. Старт API не создаёт
таблицы; миграция выполняется отдельной командой/Compose-сервисом. При отсутствии
схемы liveness доступен, readiness возвращает 503. AI не участвует в readiness.
